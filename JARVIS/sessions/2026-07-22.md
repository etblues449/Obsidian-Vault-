### 4. Hands-free auto-reply (web app)
- After a **voice** turn with a real (non-silent) answer, the mic re-arms once JARVIS finishes speaking — keep talking until a sign-off.
- Hooks the existing server-side `silent` SSE event (`lib/signoff.mjs`) → zero extra tokens, no new detection logic. Manual tap or "thanks/cheers" exits to standby.

### 5. Voice regression fixed ("call ended")
- The first UI rebuild added `navigator.mediaDevices.getUserMedia()` + a Web Audio context on the **listening** path to make the orb mic-reactive. On Samsung this collided with `SpeechRecognition` for audio focus → Android returned a "call ended" state and voice died.
- **Fix:** removed `getUserMedia` and `ensureAC()` from the listening path entirely. Orb stays reactive to TTS (the visible effect); nothing competes with `SpeechRecognition` when the mic opens. Verified: voice transcribes and answers again.

### 6. One-tap launch (no more typing in Termux)
- `~/.shortcuts/JARVIS` launcher: `termux-wake-lock` → checks if the server is up on 8737 → starts it with `nohup` if not → waits until it answers → opens `localhost:8737` in Chrome.
- Added to home screen via **Termux:Widget**. Tap the icon → server starts if down → JARVIS opens. Survives sleep (wake-lock).
- Not yet boot-persistent (needs Termux:Boot) — after a full reboot, first tap cold-starts it, which is fine.

## Key learnings
- **Don't open a second mic stream while `SpeechRecognition` is active on Samsung** — `getUserMedia`/AudioContext on the listening path steals audio focus and triggers a "call ended" state. Only touch Web Audio during TTS playback.
- **PostgREST anon role can't `count()`** — fetch rows, count in JS.
- **Fine-grained GitHub tokens default Contents to Read-only** — write returns 403 "Resource not accessible by personal access token" until you set Contents = Read **and write**. Editing the token's permission keeps the same token string (no regen needed).
- **The web connector dialog doesn't yet expose request headers** — for bearer-token MCP servers, either wait for that feature, put the secret in the URL, or (for a private personal server) make auth optional.
- SHA-verified tar.gz remains the only reliable phone deploy method; large/heredoc pastes corrupt.

## Update 2026-07-23 (late) — ⭐ Always-on wake word LIVE

**"Voice starts everything" — ✅ ACHIEVED.** Say "JARVIS <command>" with the screen off and Termux minimised; it wakes, executes, and speaks the answer. No tapping.

**Proof from the log:**
```
heard: jarvis what time
*** WAKE *** cmd: [what time]
reply: It's 22:53 (10:53 PM) on Wednesday, 22 July 2026.
```

### How it's built (and why)
- **Wake engine: none.** openWakeWord/Porcupine were ruled out — `onnxruntime` has **no installable distribution** for Termux aarch64 on Python 3.14 (`No matching distribution found`), and Vosk has the same wheel problem. Chasing them was a losing dependency fight.
- **Chosen approach:** a Bash loop around Android's own `termux-speech-to-text` (already proven working on-device, zero ML deps, £0). Continuously listens; on hearing the wake word it strips it and POSTs the remainder to the existing `/chat` endpoint, then speaks the reply via `termux-tts-speak`.
- **Wake + command in ONE breath:** early version only woke and opened the app, throwing the command away ("jarvis set a note for 5" was lost). Fixed — it now passes the command straight through to the backend and speaks the answer.
- **Bare "jarvis"** (no command) → says "Yes?" and opens the app via the existing launcher.

### The critical bug that nearly sank it
`termux-speech-to-text` **returns empty when captured via command substitution** `$(...)` — exits 0 instantly without listening, with or without `timeout`. It works fine standalone and when redirected to a **file**.
→ **Fix: always capture STT to a file, then read the file.** Never `HEARD=$(termux-speech-to-text)`.
This cost several debug cycles; worth remembering for anything else using Termux:API output.

### Files
- `~/.jarvis/wake-listen.sh` — the listener loop (file-based capture, wake-word regex, command pass-through, ensure_server)
- `~/.jarvis/wake-start.sh` / `wake-stop.sh` / `wake-status.sh` — background control (nohup + `termux-wake-lock`)
- `~/.jarvis/wake.log` — everything heard + wake triggers + replies
- Wake-word regex tolerates mishears: `jarvis|jarviss|jervis|javis|harvis`

### Known limitations (accepted knowingly)
- **Chunked listening, not continuous** — ~1–2s gap between listen cycles; a wake word landing in the gap is missed (say it again). Seamless "Hey Google"-style detection needs a native wake-word model, which the platform won't install.
- **Battery** — continuous mic + wake-lock is inherently power-hungry. Opted into deliberately.
- **Not boot-persistent yet** — needs Termux:Boot; currently start with `bash ~/.jarvis/wake-start.sh`.

### New bug spotted
- **Clock is wrong.** JARVIS replied "22:53 ... Wednesday 22 July" when the actual local time was 02:20 on Thursday 23 July. Timezone handling in the backend needs fixing (Europe/London).

## Update 2026-07-23 — clock bug fixed (stale process, not bad code)

**Symptom:** JARVIS reported "22:53, Wednesday 22 July" at 02:20 on Thursday 23rd — and worse, on a second ask two minutes later said *"Still 22:53 — only a moment's passed."* Confidently stale, and reasoning on top of the stale value.

**Diagnosis path (worth keeping):**
1. Suspected `now` was computed once at module scope → **wrong**; `systemPrompt()` in `jarvis-app.mjs` computes it fresh (line ~56) and is called per-request (line ~176). Code was correct.
2. Suspected device clock / timezone → **wrong**; `node -e "new Date()"` returned `Thursday, 23 July 2026 at 02:26` correctly, `date` agreed, `persist.sys.timezone = Europe/London`.
3. **Actual cause:** the running `jarvis-app.mjs` process had been up since ~22:53 serving **stale code in memory**. The file on disk was fine; the process wasn't.

**Fix:** `pkill -f jarvis-app.mjs` then relaunch. Verified: `"It's 02:27 on Thursday, 23 July 2026"` — correct.

**⚠️ Footgun to remember:** the wake listener's `ensure_server()` only starts the server **if it's down** — it never restarts a running one. After any code change to `jarvis-app.mjs` (or anything it imports), you MUST kill the process; otherwise the old build keeps serving indefinitely and you'll debug phantom bugs. Consider adding a `jarvis-restart` helper.
