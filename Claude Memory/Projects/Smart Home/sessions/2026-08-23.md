## 2026-08-23 — PHASE 3 COMPLETE: durable memory (verified on device)

### The gap, proven not assumed
`lib/memory.mjs` rewrote the ENTIRE fact file with a single `writeFileSync` on every
`remember`/`update`/`forget`. Demonstrated consequence in the sandbox: seed 5 facts, interrupt the
write mid-way → **0 facts survive**. The risk was never losing one memory; it was losing all of them
to a battery-kill or Doze at the wrong moment. It also never verified the write — `addFact` returned
`{id,text}` unconditionally, so JARVIS could truthfully-sounding say "I've remembered that" about a
write that never landed.

Recon corrections along the way (both stale beliefs in this vault):
- `jarvis_memory.md` **does exist** (458 B, 1 fact). The older "no fact has ever been stored" note is
  wrong; the 2026-08-22 audit was right.
- `memory.mjs` contains **no git commit** — an earlier grep for "commit|push" matched only
  `lines.push`. Facts land in the working tree; obsidian-git carries them.

### The fix
Every mutation is now:
1. **Atomic** — sibling temp file → `fsync` → `rename`. Readers see the old file or the new one,
   never a half-written one.
2. **Backed up** — previous good file kept as `jarvis_memory.md.bak` before the swap.
3. **Read-back verified** — the file is re-read from disk and the intended change confirmed.
   Failure restores the backup and throws. `addFact` returns `verified: true` only when the fact is
   provably on disk; `updateFact`/`removeFact` return `{ok:false, reason}` rather than lying.
4. **Mass-loss guarded** — if any single edit drops more than one fact, restore and abort.

New export `memoryHealth()` → `{ok, path, facts, backup, staleTemp}`.

**Deliberately NOT added: a git commit.** C-constraint is a single write path (obsidian-git on
`master`); a second committer is what corrupted the vault before.

## 2026-08-23 — PHASE 4 COMPLETE: the execution gap closed (verified on device)

### The gap, in the code
`jarvis-app.mjs:67` — `const pending = new Map()`. The confirmation flow parked the `resolve`
function in **process memory** and waited for a browser POST. If the app died in that window (Doze,
battery kill, restart), the Map vanished: the approval arrived, `pending.get(id)` was `undefined`,
and **nothing happened, silently**. An action could also die mid-run with no record it ever started.

### The fix — `lib/ledger.mjs`
Append-only JSONL ledger, written BEFORE the gate opens and again after the outcome. Every state is
a fact on disk, nothing inferred:

    proposed -> approved|declined -> started -> ran|failed
    (terminals also: blocked [hardline/safe-mode], expired)

Wired into `lib/agent.mjs` — the ONE shared core — at 7 points, so text, app, voice and heartbeat
all inherit it. `fsync` on every append. Appends chosen over rewrites deliberately: an interrupted
append can lose at most the last line, never the history.

New: `jarvis-ledger.mjs` CLI (`open` | `recent N` | `expire N` | `compact` | `path`).

### THE SAFETY DECISION — no auto-replay (locked)
An approval that never executed is **not** resumed on the next boot. Jelly Bean approved an action
*at a moment*; silently firing it hours later, after a reboot, in a different context, is exactly the
unrequested action this project forbids. `drainReport()` is READ-ONLY (asserted in the test suite:
calling it adds zero records and does not resolve the orphan). Orphans are surfaced for re-approval.

### Two bugs caught by my own tests, before the phone saw them
1. **Exact-indent anchors.** The patcher assumed 6 spaces on two `audit(...)` lines; the real file

## 2026-08-23 — ROOT CAUSE FOUND: obsidian-git deleted the entire Actions engine

### What was actually wrong
Captures had been idle since **2026-07-09** and briefings stopped at **2026-08-04**. The cause was
not Tasker, not the n8n webhook, and not the runner — **`.github/workflows/` did not exist on
`origin/master` at all.**

    4bdb3bf1  Sync from Obsidian (Jarvis ): 2026-08-06 04:17 UTC — 0+ 1~ 6-
      D .github/workflows/_jarvis-run-skill.yml
      D .github/workflows/jarvis-1-morning-brief.yml
      D .github/workflows/jarvis-2-capture-router.yml
      D .github/workflows/jarvis-3-connection-finder.yml
      D .github/workflows/jarvis-4-weekly-synthesis.yml
      D .github/workflows/jarvis-6-pattern-detector.yml

**This was the THIRD occurrence**, not the first: `7f9097d9` (2026-07-04, 2 files) and `9fd5e00e`
(2026-07-14, 5 files) did the same thing. Every time, an obsidian-git "Sync from Obsidian" commit
removed workflow files.

**Mechanism:** Obsidian does not index dotfolders, so `.github/` is invisible to it. obsidian-git
runs `git add -A` from the vault root; anything not present in Obsidian's view is staged as a
deletion. The engine deleted itself, quietly, and every scheduled run simply had nothing to trigger.
Last successful run before the outage: **JARVIS Morning Brief, 2026-08-05T09:30Z**.

This also explains an older open item — the "8 files deleted from master on 2026-08-02 by an
unidentified client". Same mechanism, same culprit. No mystery client.

### Fixed
1. **Restored all six workflows** from `a38848c9` (last good state) → commit `ededb34e`, pushed as
   `ef8b96cc..167427db`. Verified present on `origin/master` via `git ls-tree`.
2. **Pre-commit hook installed** at `.git/hooks/pre-commit` — refuses any commit that stages a
   deletion under `.github/`. Hooks are local and untracked, so obsidian-git cannot remove it.
   **Proven live:** a real deletion of `jarvis-1-morning-brief.yml` was staged and the commit was
   REFUSED (`x COMMIT BLOCKED`); all 6 files remained. Override is `git commit --no-verify` if ever
   genuinely intended.
3. **`.gitignore` added** for the Phase 3 device-local artefacts
   (`jarvis_memory.md.bak`, `.tmp-*`) so atomic-write backups never sync.

### Proven working end to end
A real capture written to `JARVIS/Inbox/` and pushed →
**JARVIS Capture Router — completed, success, 2026-08-23T02:49:00Z**.

### The lesson (generalises beyond this repo)
A vault synced by a tool that cannot see part of its own working tree will delete that part. Any
path Obsidian doesn't index — `.github/`, `.claude/`, hooks, CI config — is at permanent risk under
`git add -A`. The pre-commit hook is the durable defence; recording it here so the next session does
not re-diagnose this from scratch a fourth time.
