## 1 · Hard constraint on cloud sessions — read this before planning anything

**A Claude Code session running in the Anthropic cloud container cannot reach the house.**
Probed and confirmed this session:

- `curl http://192.168.0.200:8123/` → **times out** (no route)
- `curl http://192.168.0.201/` → **403 from the egress proxy**, not from the board.
  Do not read that 403 as "the board answered" — it did not.
- The proxy's `noProxy` list includes `192.168.0.0/16`, so LAN addresses are attempted
  direct, and there is no route.

**Consequence:** a cloud session can write configs, diagnose from pasted logs, and
commit to the vault. It **cannot** restart add-ons, SSH to the Green, flash a board, or
verify anything on hardware. Do not offer to. Ask Elliot to run the commands, or work
from a session on the PC.

Earlier in this session the user asked to "take control of this PC" — that is not
possible from here, and saying so early saves a lot of wasted turns.

`priority: 700` → `620` in the `on_boot` hook, then restart the count.

### Root cause, for the record

`ESP_ERR_NOT_SUPPORTED` on `.201` was **EXIO3 power-gating**, not a bad sensor. The
CH32V003 I²C expander held the camera powered down until a `priority: 700` `on_boot`
hook drove EXIO3 low and **blocked** for 300 ms before `esp32_camera` initialised. The
blocking lambda is the point — an async `delay:` does not work here.

Ruled out and **not** to be revisited: sensor replacement (JPEG engine confirmed present
— `Pixel Format: JPEG` only prints on a successful init), ESPHome downgrade, hardware swap.

## 3 · The live blocker — Frigate add-on go2rtc crash loop

Full diagnosis: [[../fixes/2026-08-21-frigate-go2rtc-crash-loop]]. Summary:

**Two misreadings to avoid — both were made and corrected this session:**

1. **"HA is slow booting."** It is not. HA is healthy — it served live entity state at
   21:38 and is routing ingress traffic. Waiting is not a fix and never was.
2. **"The `.201` reboots broke go2rtc."** They did not. go2rtc starts fine against a
   dead source; it binds its ports and marks the stream offline. An unreachable camera
   cannot stop it binding `1984`.

**What is actually happening:** go2rtc dies at startup before binding port `1984`, every
cycle, emitting no output of its own. The add-on watchdog restarts it; s6's finish script
then times out (`sending it a SIGKILL`), which leaves a process that may still hold
`1984`/`8554` — so the next instance cannot bind either. Self-sustaining. Frigate is
gated behind go2rtc in the s6 chain, so Frigate never starts, so its auth service on
`5001` never binds, so nginx returns **502 on everything** — which is every error in the
log Elliot pasted.

Ports `5000`/`5001` in those errors are **inside the add-on container**, not HA.

**Recovery ladder — stop at the first step that works:**

1. **Full stop → verify "Stopped" → start.** Not *restart* — restart may not clear a
   process s6 cannot reap.
2. **Comment out the entire `go2rtc:` block**, stop/start. Comes up ⇒ that block is the
   culprit; re-add streams one at a time. Prime suspect is an unquoted `#` — YAML
   truncates `ffmpeg:http://...:8080#video=h264` at the `#` unless the value is quoted.
3. **Reboot the host.** Clears a zombie holding the ports. If it loops straight after a
   host reboot, another add-on owns `1984`/`8554`.
4. **Reinstall the add-on.** Recordings are safe (share/media, not the container).
   **Copy `frigatestandalone.yml` off the Green first.**

## 4 · The Frigate config to add — ready, verified against the ESPHome file

Only after the add-on comes up clean. Both edits go in `frigatestandalone.yml`.

**go2rtc stream** — note the quotes:

```yaml
go2rtc:
  streams:
    ai_cam_outside: "ffmpeg:http://192.168.0.201:8080#video=h264"
```

**Camera**, alongside the existing `ai_cam:` under `cameras:`:

```yaml
  ai_cam_outside:
    ffmpeg:
      inputs:
        - path: rtsp://127.0.0.1:8554/ai_cam_outside
          roles: [detect, record]
    detect:
      width: 800
      height: 600
      fps: 5
    objects:
      track: [person]
    record:
      enabled: true
      retain:
        days: 14
    snapshots:
      enabled: true
```

**Two deliberate changes from the older block in
[[../fixes/2026-08-04-ai-cam-outside-camera-init]]:**

- `rtsp://127.0.0.1:8554/...` instead of `rtsp://192.168.0.200:8554/...`. The old form
  sends Frigate's own traffic out to the LAN IP and back into the same container.
  `127.0.0.1` is what Frigate documents for a go2rtc restream and removes a failure mode.
- The go2rtc URL is **quoted**. Unquoted, YAML eats `#video=h264`.

**Verified against [[../hardware/ai_cam_outside.yaml]] this session:**
`resolution: 800x600` (L372), `jpeg_quality: 12` (L373), `max_framerate: 5 fps` (L374),
`esp32_camera_web_server` → `:8080` stream / `:8081` snapshot (L383+). So
`detect: 800x600 @ 5fps` is correct. **Change the camera resolution and you must change
`detect:` with it**, or detection silently misaligns with the frame.

**One-client constraint:** the board serves exactly one stream client at a time. go2rtc
must be the only consumer of `:8080`. Close any browser tab sitting on
`http://192.168.0.201:8080` before testing.

`media_player: - platform: speaker, name: "AI Cam Outside Speaker"` — an exact match, and
the only known source of that entity name. **The board is running that file, not the one
the vault held.** The index's "winner" decision was therefore resting on a stale premise.

**Action taken:** that file has been **promoted into the vault** at
[[../hardware/ai_cam_outside.yaml]], replacing the stale copy. It was living in an
ephemeral scratchpad that dies with its container — one more session and it was gone,
leaving the vault permanently disagreeing with the hardware. Git holds the old copy.

**What the promoted file adds** over what the vault had: `voice_assistant:`,
`micro_wake_word:` (`hey_jarvis`), `sdmmc:` + SD card, `speaker:`, `media_player:`,
`fast_connect: false`, `agc_gain_ceiling` 2x → 8x for night, logger over USB_SERIAL_JTAG,
and no `ap:`/`captive_portal:` (their absence is deliberate — `ap:` needs
`ap_fallback_password` in secrets and fails **validation** without it, which is what broke
an earlier build).

**This retires the old "port voice/SD features across from landing_ai_cam_2 one at a
time" action** — the promoted file already carries them, from a base proven on the
living-room board with the same camera + wake-word + SD combination, so the memory budget

**Still worth one check:** the running image self-reports `compiled 2026-08-02 01:02:49`.
Confirm the Device Builder last-install timestamp for the device is **on or after

## 6 · Not touched this session — `.199` AI Cam (living room)

**Off the network since 2026-08-06.** Different fault class from `.201`; deliberately
left alone while `.201` was in flight. Do not conflate the two.

Observed symptom: go2rtc reporting
`Connection to tcp://192.168.0.199:8080 failed: No route to host`.
**`No route to host` = EHOSTUNREACH — the host is unreachable.** A camera that was
merely failing would give *connection refused*. It worked 2026-08-05, so this is a
change, not a long-standing fault.

**Cause not established — do not record one until observed.**

**Leading theory (carried forward from the 2026-08-21 PR check-in) — the `fast_connect`
channel trap.** The living-room `ai_cam.yaml` carries `fast_connect: true`, and the
board vanished on **2026-08-06**. `fast_connect` skips the AP scan and reconnects
straight to the channel/BSSID cached in **NVS**. If the Hub 5's Channel Optimization
moved the 2.4 GHz channel, the board keeps retrying a channel that no longer carries the
SSID — and because the cache lives in NVS it **survives reboots**, so `reboot_timeout`
cannot heal it. That matches the symptom precisely: **EHOSTUNREACH, not ECONNREFUSED**.

The fix is `fast_connect: false` — already written, **never flashed**. It needs USB,
because a board that cannot join the network cannot take an OTA. Note the promoted
[[../hardware/ai_cam_outside.yaml]] already sets `fast_connect: false` for `.201` and
names this trap in its header, so `.201` is not exposed to it.

Other candidates, cheapest first:

1. Board hung → power-cycle it.
2. An `ai_cam` flash during the 2026-08-04 Device Builder session (its build server
   showed **2 active jobs**, one being AI Cam Outside — the second was never
   identified). This would cross the standing *do not reflash ai_cam* constraint. Check
   the last-install timestamp against the known-good **2026-07-30** build.
3. IP collision at `.199` — `ai_cam.yaml` sets `manual_ip` with **no DHCP reservation**,
   so the router can reassign it. Same class as the open `.171` collision.

**DHCP reservations still owed on both boards** (neither has one, so the router can
reassign either at any time): `.201` MAC `28:84:85:49:86:70`, `.199` MAC
`28:84:85:49:83:C8`.
