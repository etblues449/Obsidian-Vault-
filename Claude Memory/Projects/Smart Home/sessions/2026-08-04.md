# Session B — Task 3: Assist two-way audio → automations

Scope was Task 3 of the 2026-08-04 three-task handoff only. Tasks 1 (WebRTC card) and 2
(`ai_cam_outside` camera) were not touched by this session.

## What was done

- Built `ha-config/packages/jarvis_assist_person.yaml` — one HA package containing 4 MQTT
  entities, 3 helpers, 1 notification script and 5 automations covering all four items the
  handoff asked for (person→light on, clear→light off as a separate automation, away-mode
  spoken alert, privacy switch, and the `ask_question` challenge with answer-id branching).
- Wrote `Assistant Core/ha-diagnostics/test/validate-assist-package.py` — offline structural
  and entity-boundary validation, no hub required.
- Wrote `Assistant Core/ha-diagnostics/assist-preflight.mjs` — read-only live verification
  against the hub, in the same zero-dep style as `ha-doctor.mjs`.
- Wrote the runbook: [[../automations/2026-08-04-assist-person-automations]] — install
  order, design decisions, and a five-step test protocol (A–E) that maps onto the handoff's
  "done when".
- Created `ha-config/` with a README. **This is not the hub backup** — nothing was pulled
  off the hub, so Session A's P0 stays open in full.

## What was NOT done, and why

**Nothing has run on the HA Green.** `192.168.0.200` is a LAN address and the build session
runs in a remote container; the connection times out. So the completion bar in the handoff —
*"the challenge automation runs end-to-end with its trace showing a matched answer id"* — is
**not met and cannot be met from here**. Install and tests A–E are the remaining work and
must be done on the LAN.

| Same validator on 5 deliberately-broken copies | all 5 fail correctly, exit 1 |

The negative tests are the point. Injected regressions caught: an answer id becoming a bare
`no` (YAML boolean), an unguarded `reply.id` read, a removed cooldown delay, a reverted
`person.elliot`, and automations 2 and 4 losing their mutual exclusion.

## Decisions made

- **Package, not `automations.yaml`.** The Frigate HA integration is not installed, so
  Frigate's detections exist only as MQTT topics, and MQTT entities cannot be created from
  the automation UI. A package keeps entities, helpers, script and automations installable
  and removable as one unit.
- **Frigate's person count is converted to a `binary_sensor` once**, and every automation
  triggers on the `off`→`on` edge. This fixes "every MQTT count update re-triggers it" at
  the source instead of guarding against it in five places, and unlocks `for:` durations.
- **Cooldown = `mode: single` + a trailing `delay`.** No helper, and specifically no
  self-referencing `last_triggered` template, which breaks silently when an alias is renamed.
- **Automations 2 and 4 made mutually exclusive** via `input_boolean.ai_cam_simple_alert_only`
  — a deviation from the handoff's flat list. Built literally they would fire together on one
  satellite with one speaker, and the challenge would lose its answer to the announce talking
  over it. The validator asserts the guards stay opposites.
- **Privacy-follows-presence ships inert.** Enabling it stops detection while home, which
  also silences the person→light automation while home. Real trade-off, Elliot's call.
- **`start_conversation` still not used.** Unblocking it means pointing the pipeline at the
  "Claude" conversation agent, which routes all voice commands through the LLM. That is a
  standing decision, not something an automation file should change silently. `ask_question`
  bypasses the conversation engine entirely and needs none of it.
- **The unresolved legacy notify service name is resolved by tooling, not guessed at.**
  The text alert always goes out over the verified `notify.send_message` entity path first;
  the image attachment is a best-effort second call, so a wrong guess costs the picture, not
  the alert. Preflight enumerates the hub's real `notify.mobile_app_*` services and names the
  correct one.
