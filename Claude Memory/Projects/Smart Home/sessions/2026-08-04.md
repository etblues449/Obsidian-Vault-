### Debug (fault-diagnosis protocol, evidence-first)

- **Root cause re-confirmed and extended:** `0x106` = power, not pins — OV3660 gated by
  CH32V003 EXIO3 (active-high, 10K pull-down); stock CameraWebServer never touches the
  expander. All three transcript pinouts belonged to other boards.
- **NEW: vendor's own Arduino example found** (`waveshareteam/ESP32-S3-CAM-OVxxxx`,
  `Arduino-v3.2.0/examples/02_CameraWebServer`, Apache-2.0): real pins hidden in the
  `CAMERA_MODEL_ESP_EYE` slot; io_extension driver drives EXIO3 LOW + EXIO6 HIGH.
  Pin map re-verified against BSP header lines 113–124 — zero mismatches.
- **Arduino path now COMPILE-PROVEN** (was "logically correct, untested"): adapted vendor
  sketch builds clean on esp32 core 3.3.11 — 1,026,695 bytes (32% of 3MB app). Delivered
  as `WS_S3_CAM_OV3660_WebServer.zip` + README (IDE settings incl. OPI PSRAM).
- **Board-2 hypothesis recorded:** the transcript's successful uploads most likely
  overwrote the 2nd CAM board's ESPHome firmware → why `landing_ai_cam_2` is unavailable.
  Confirm via MAC (`…83:C8` = live ai_cam; `…86:70` = presumed board 2).

## Session 2 — handoff Task 1: WebRTC card

### Scope

Task 1 of the three-task handoff only. Tasks 2 (`ai_cam_outside` camera init) and 3
(Assist two-way audio → automations) untouched.

### Constraint that shaped the outcome

No LAN and no Nabu Casa access to `192.168.0.200` from this session. Nothing was observed
on the live hub. So the deliverable is a **source-verified diagnosis plus a corrected,
tested card config** — not a working card. Every "verified" claim below is from source
read on 2026-08-04; the live-instance steps are listed as still-open.

### What was done

- **Pinned the installed integration version to `v3.6.1`** from the served build's
  `video-rtc.js?v=1.9.9` import, by checking that import across every recent tag
  (master=1.9.12, v3.6.1=1.9.9, v3.6.0=1.9.4, v3.5.x=1.8.0). `__init__.py` is
  byte-identical v3.6.1→master; `utils.py` differs only in `BINARY_VERSION`. So the read
  is authoritative for this install.
- **Ruled out** the plausible "integration predates HA's `hass.data["lovelace"]`
  dataclass change" theory — v3.6.1's `init_resource` already carries the
  `hasattr(lovelace, "resources")` guard.
- **Established the mechanism**: `async_setup` serves the JS (step 1) and registers the
  Lovelace resource (step 2) as independent sequential operations. Fetching the JS
  successfully proves only step 1. The decisive diagnostic is the resource list, not the
  integration's presence.
- **Corrected two errors in the handoff's next steps** — `create_link`/`dash_cast` are
  registered in `async_setup` step 6 (not `async_setup_entry`), and the JS serving is
  itself evidence a config entry already exists, because `config_flow: true` means no
  entry → no `async_setup` → 404.
- **Found and fixed two real bugs in the proposed card config:**
  1. `poster: /api/camera_proxy/...` → leading `/` sets `poster_remote=true` → assigned
     straight to `<video poster>` → unauthenticated → HA core's `CameraView` raises
     **403**. Fixed to the bare entity id, which routes through the card's signed
     `ws_poster` path.
  2. The templated icon dereferenced `states[...].state` unguarded. `renderTemplate`
     swallows the resulting `TypeError` in a `catch` that only `console.debug`s, so a
     missing entity **silently deletes the entire shortcuts row**. Fixed with `?.`, and
     the template value quoted so the YAML `": "` trap disappears.
- **Wrote a verification harness** replicating v3.6.1's `setConfig`, `poster_remote`
  derivation, `ws_connect` URL construction, the full template pipeline across four
  entity states, and shortcut dispatch. Corrected card: 12/12 pass. Original handoff
  card: 2 failures, exit 1 — so the harness is proven to detect the bugs rather than
  passing vacuously.
