## The constraint that shapes everything

The Obsidian CLI is a **client**, not a vault reader. It opens a socket to a
running Obsidian desktop app and asks it to act. No app running, no CLI. So
"setting up the skill" means installing and running the desktop app wherever the
CLI is meant to work, not installing a CLI package.

No device bridge in this session — the cloud container cannot reach the PC or the
Fold. So the work split in two: make it genuinely work here, and ship a tested
setup path for the PC.

## Three findings worth keeping

1. **The "Command line interface" toggle is just `"cli": true`** at the top level
   of `obsidian.json` (`~/.config/obsidian/` on Linux, `%APPDATA%\obsidian\` on
   Windows). Found by reading the ipc handler in `obsidian.asar`. That is what
   lets both setup scripts here enable it without touching the GUI.
2. **`XDG_RUNTIME_DIR` is the trap.** The socket is
   `$XDG_RUNTIME_DIR/.obsidian-cli.sock`, falling back to `$HOME`. Containers
   hand out an inconsistent value between shells, so the app creates the socket
   in one place and the CLI looks in another — presenting as "unable to find
   Obsidian" while the app is plainly running. Both wrappers unset it.
3. **Electron segfaults if it beats the X server up.** A fixed `sleep 2` after
   starting Xvfb worked once and then segfaulted on a cold run. The launcher now
   waits for `/tmp/.X11-unix/X99` and retries the app up to three times. Caught
   by deliberately tearing the environment down and re-running, not by guessing.

## Safety check — auto-writer plugins

`obsidian-git` is enabled in this vault with `autoSaveInterval: 10`,
`autoPushInterval: 10`, `autoPullOnBoot: true`, `disablePush: false`. A headless
instance loading it would be an unattended client pushing to `master` every ten
minutes — the same shape as the still-open *"identify the client that deleted 8
files from master"* item.

Checked, not assumed: `app.plugins.plugins` is **empty** (Obsidian opens an
untrusted vault in Restricted Mode) and the clone stayed **0 commits ahead of
origin**. The bootstrap now asserts this every run and calls
`app.plugins.disablePlugin()` — the runtime-only call — on anything risky that
did load.

## Addendum — a fourth finding, caught by re-running

The suite went 19/20 on one cold run: **`tags with counts` returned nothing**.
Not flakiness to retry away — the socket answers as soon as the app is up, but
tags, backlinks and search are served from the **metadata cache**, which is still
being built for the first several seconds. Commands that depend on it return
empty, which looks exactly like a broken setup.

Fixed at the source in both scripts: poll

```js
app.metadataCache.initialized
  && app.metadataCache.inProgressTaskCount === 0
  && app.metadataCache.getCachedFiles().length >= app.vault.getFiles().length
```

before declaring ready. On this vault it resolves in **7–8 seconds**.

Also added: the bootstrap now answers the first-open *"Do you trust the author of
this vault?"* dialog by clicking **Browse vault in Restricted Mode**. CLI commands
worked behind the open modal, but a pending modal is a pending decision — and
Restricted Mode is the answer that keeps `obsidian-git` off.

### Three things running it on real hardware exposed

The script had been parse-checked and unit-tested but never executed. Every one
of these would have stayed hidden:

1. **Wrong install root.** Obsidian's per-user NSIS installer lands in
   `%LOCALAPPDATA%\Programs\Obsidian`, not `%LOCALAPPDATA%\Obsidian`. The script
   reported "not found" on a perfectly normal install. Now it checks the right
   roots first, then the running process, then the uninstall registry.
2. **`Join-Path` crash on a null root.** `ProgramFiles(x86)` is absent on this
   machine, and `Join-Path` is evaluated *before* any filter placed after it —
   so the null guard has to sit on the base, not the joined result. Symptom was
   `Cannot bind argument to parameter 'Path' because it is null`.
3. **PowerShell 5.1 read `obsidian.json` as ANSI, corrupting the vault path.**
   This one actually broke things: the vault is
   `Jelly Bean's Vault — primary` with an **em dash**, and the naive
   `Get-Content -Raw` → edit → write round-trip mangled it. Obsidian could no
   longer find the vault and opened the picker instead. Caught immediately
   (`obsidian version` → *"Vault not found."*), and **repaired from the backup
   the script takes before editing** — restored, re-applied with a proper UTF-8
   read/write, and verified `PATHS_MATCH_BACKUP: True` plus the vault reopening
   by name. The corrupted copy is kept at `obsidian.json.corrupt` if you ever
   want to see it.

All three are fixed on `master`, each with a regression test — including one
that round-trips a path containing an em dash, which is the exact failure.
Test count went 16 → 33.

**The lesson worth keeping:** "parse-checked and unit-tested" was not the same
as "works". Three real defects sat in a script that passed every test I could
run without the target machine. Where a deliverable can be executed on the real
target, execute it.
